# ADR-018: 原型升级为可点击的全路径仿真，UI 走增量确认

## Status

Accepted

## Context

用户对 `PSP-W1` 的第三条经验（2026-09-23）：

> **UI 设计质量太差**。经验：遗漏了很多细节，需要后补充。再来一次的话：**UI 也是增量式确认**；把 mockup 变成**真实可点击、覆盖全路径的仿真**，早发现问题。

本批实证：

| 现象 | 证据 |
|---|---|
| UI 在交付后被动返工 | Sprint 4 `#5`「UI 迭代与设计系统收口」记录为**三轮用户反馈驱动**（色系 / 版式 / 外框冻结）才闭环 |
| 「遗漏细节、后补」是主要形态 | 原型侧一轮审计就发现 **5 处**「类名在原型里用了、CSS 里没有规则」（`.dialog-actions` / `.dialog-target` / `.btn-danger` / `.section` / `select`），表现分别是贴死 / 无区别 / 破坏性按钮与主按钮同形 / 标题贴上文 / 下拉框原生 19px |
| 交互路径类缺陷只能等真实实现才暴露 | 相对链接导致「点第二次就 404」（Issue 5）、重名报错被弹窗遮罩盖住（看不到报错）、长值撑出弹窗边框（Issue 8）、目标块在宽弹窗里留白难看（评审）—— 这些都是**路径与版面**问题，而原型是静态页 + 静态断言（134 项），走不到这些路径 |
| 静态断言给了「已验」的错觉 | 134 项断言全绿，但断言的是**渲染结果**，不含「点两次 / 提交后落点 / 错误落在哪里 / 刷新后状态」 |

根因：**原型是「可看」的，不是「可走」的**；而 UI 缺陷恰恰集中在「走过去」的过程里。

## Decision

1. **原型必须是可点击的全路径仿真**：每个入口都能点到；关键路径在原型里就能走完，至少覆盖 —— 成功路径、失败路径、**刷新后状态**、返回/取消、以及**同一入口的第二次操作**（本批 Issue 5 正是这一条）。
2. **UI 走增量确认**：每个 UI 相关的 SBI 交付后**当批确认**（当批给出可点的原型 + 截图），不得累积到批次末或交付后由用户一次性发现。
3. **原型断言从「静态渲染」扩展到「交互路径」**：把上述路径写成断言（点第二次不 404、提交后落在哪里、错误显示在触发它的上下文内、刷新后状态如何）并纳入原型验收脚本。
4. **两份 CSS 必须逐文件一致（sha256）**，且**新增组件必须同时登记「缺失规则时的表现」**（沿用既有纪律，避免再次出现「类名在、规则无」）。
5. **原型仿真不替代实现侧护栏**：布局与几何断言仍必须在真实实现上跑（见 Issue 8：原型断言全绿的同时，实现侧的值仍然撑出了边框）。

## Rationale

- **发现点前移**：用户原话是「尽可能在 mockup 阶段就发现问题」。样式与版面的改动成本在原型阶段最便宜，在实现之后最贵（本批三轮 UI 返工即为代价）。
- **与「UI 增量式确认」同向**：UI 评审是**主观反馈**，主观反馈的收敛只能靠**多轮小步确认**；一次交付一大坨 UI，用户只能给出笼统的「太难看 / 太密」，而笼统反馈又无法直接变成改动（本批是靠自建度量脚本把主观反馈转成数字才收敛的）。
- **不选「继续用静态原型 + 更多静态断言」**：静态断言无法覆盖路径与交互（本批已证明它会给假绿）。
- **不选「直接看真实实现评审」**：真实实现里业务逻辑与 UI 纠缠，改版面的成本高，而且会与「批次可独立验收」冲突。

## Consequences

- **正面**：UI 缺陷更早、更便宜地暴露；评审对象从「截图」变成「能点的东西」；交互路径缺陷（点两次、错误位置、刷新状态）进入自动化验收。
- **代价**：原型要做交互与四语言，工作量上升；需要维护一份**关键路径清单**，否则「全路径」会退化为口号。
- **风险**：原型是仿真，**不等于实现** ⇒ 实现侧必须保留独立断言（本 ADR 第 5 条）；原型与实现的行为差异要显式登记，不得靠「看起来一样」。
- **后续**：`portal-identity-plan.md` §8 的 `SBI-P1`–`SBI-P3` 按本条执行（新增开发登录页与 401 自诊断块、同步 Issue 1–5 界面修正、同步本轮版式并复跑断言）。
