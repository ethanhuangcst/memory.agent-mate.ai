# ADR-005: 升级准入判据分层 —— 硬性阻断（H）与人工确认（W），且闸门必须「可通过」

## Status

Accepted

## Context

产品需求（用户原话）要求：*「在更新策略中加入更新筛选条件，当条件不满足的时候提示『该版本尚不稳定，不适合更新』」*。

第一版设计把 6 条判据**全部**设为硬性阻断，其中 H5 = 「候选 commit 无失败 check-run」。
接入真实数据后立刻暴露设计缺陷：

- **所钉的 v0.10.0 自身就有 1 项失败的 check-run**（`publish @alphaone/ai-memory to npm`）。
- 本部署消费的是**镜像**，而「镜像构建成功」已由「GHCR 上存在该 tag 的镜像」这一条直接证明。
- 上游在同一个 release commit 上还跑 npm / PyPI / Homebrew / mobile 等**与本部署无关**的发布 job。
- 结论：**一个永远无法通过的闸门不是闸门，是死锁** —— 任何未来的升级都会被无关失败卡住。

同时还有两个现实约束：

- **H6（新鲜外迁备份）在本地/CI 无法求值**（备份在服务器侧**阿里云 OSS**），只能人工确认。
- 上游历史上出现过 secure-by-default 翻转（v0.9 attestation），这类变更**需要人读 CHANGELOG** 判断，
  不适合用正则硬判。

## Decision

准入判据分**两级**，并定义**契约化退出码**与**固定话术**：

### 硬性阻断（任一命中即不通过 → exit 2）

| 编号 | 判据 | 理由 |
| --- | --- | --- |
| H1 | 非预发布版（`prerelease=false && draft=false`） | 上游 `release.yml` 明确：预发布版**不产出 GHCR 镜像**，升了也拉不到 |
| H2 | 沉淀期 ≥ `SOAK_DAYS_MIN`（锁文件，默认 14 天，可配） | 新版本暴露缺陷需要时间窗口；本部署迁移**前向-only** |
| H3 | GHCR 上存在对应 tag 的镜像 | 无镜像 = 无法部署（同时也是「构建成功」的证明） |
| H4 | 候选版本不早于当前所钉版本 | 防「升级」成降级 |
| H5 | 存在新鲜外迁备份（**服务器侧人工确认**） | 回滚只能靠快照，无备份则无退路 |

### 人工确认（不阻断，但必须逐条读 → exit 3）

`W1` CHANGELOG 破坏性关键词 · `W2` schema 前向迁移 · `W3` 契约面差异 ·
`W4` 镜像标签被重推 · `W5` 版本跨度 ≥2 minor · **`W6` 候选 commit 失败 check-run**（本次由 H 降级而来）

### 退出码契约（调用方据此分流，禁止解析 stdout 文案）

`0` 无新版 · `2` 命中硬性阻断 · `3` 可评估升级 · `1` 运行错误

### 提示话术（固定，禁止改写语义）

```
❌ 准入判定：不通过
   ai-memory vX.Y.Z —— 该版本尚不稳定，不适合更新
   不满足 H2 沉淀期 ≥ 14 天：已发布 3.2 天（阈值 14 天）
   建议：沉淀期不足：建议 2026-10-05 之后重跑 make preflight。
```

## Rationale

- **闸门的可用性优先于闸门的严格性**：判据若不可通过，人就会绕过它，安全价值归零。
  check-run 失败是「上游自己的发布流水线噪音」，不是「我们的部署风险」——归入人工确认。
- **硬性阻断只放「客观、可自动求值、且直接决定能否运行」的条件**；凡是需要语义判断的（破坏性变更）
  归入人工确认。
- **退出码而非文案**做分流契约：文案会被人改，退出码不会；GitHub Actions 与 shell 都据此分支。
- **沉淀期可配**（锁文件 `SOAK_DAYS_MIN`）：给保守与激进两种运维节奏留出口，而不改代码。

## Consequences

- 闸门可实际通过（`make preflight` 对当前 0.10.0 输出 exit 0）。
- 上游发新版时 Actions 能稳定分流：`exit 2` → `upstream-unstable` 标签 +「尚不稳定」标题；
  `exit 3` → `ready-to-upgrade` 标签。
- 判据规格（`deployment.md` §9.4 告警项 W1–W6）与执行体（`upstream-preflight.sh`）**同源**，变更须同步。
- 注意：人工确认项依赖人的纪律：`exit 3` 不等于"可以升"，必须逐条读 W 清单。
- 注意：H5 无法自动求值 → 在任何自动化结论里都显示为「未判定」，需人工在服务器侧用 `ossutil ls` 补上。
- 注意：附带发现（非本 ADR 决策但受其约束）：**回滚必须用 pre-migration 快照覆盖 DB**。
  上游**不会**因「库比二进制新」而拒绝启动（`src/storage/migrations.rs:1507`：`version >= CURRENT_SCHEMA_VERSION`
  时直接 `return Ok(())`；全 `src` 无拒绝逻辑），故只改 `IMAGE_TAG` 的「回滚」会让旧二进制
  静默操作它不认识的 schema。该约束已写入 `deployment.md` §10（回滚）。
