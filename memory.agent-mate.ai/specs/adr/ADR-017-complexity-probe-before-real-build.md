# ADR-017: 技术复杂度高的工作先开探针 SBI，再开真实开发

## Status

Accepted

## Context

用户对 `PSP-W1` 的第二条经验（2026-09-23）：

> 技术复杂度高的工作应该进一步分解，**先设探针验证，再开真实开发**。

本批的实证支持这条判断。`PSP-W1` 里技术复杂度最高的两项 —— **cloudflared 隧道 + Cloudflare Access 真身份**、**身份来源收口（真实邮箱 + 生产护栏）** —— 都不是与普通功能同批推进的：前者在推进过程中出现过一次**代价明确的误判**，我在**没有读配置、没有看进程**的情况下先下了「本机网络不通 / cloudflared 装不上 / 真身份路径未接通」的结论并写进了文档与建议，事后逐项实测全部推翻（DNS 与 HTTPS 通、`cloudflared` 早已安装并授权、隧道 `portal-dev` 正在运行、`admin_portal/.env` 里团队域与 `AUD` 已是真实值）。真因是与业务逻辑无关的一件小事：**启动配置与隧道目标不匹配**。

值得注意的是：**这些结论本来用几条命令就能证伪**（`scutil --dns` 与本机 `/etc/resolv.conf` 对照 · `dig @<公共 DNS>` 对照解析 · `curl -w '%{http_code}'` 看可达性 · `cloudflared tunnel list` 看隧道 · 直接读 `admin_portal/.env`）。问题不在于难，而在于**没有先开一个「只回答一个问题」的单元**，于是不确定性被直接带进了真实开发与文档。

## Decision

1. **判定口径**：满足以下任一条件的工作，标记为「技术复杂度高」——① 首次引入外部系统或第三方行为不确定；② 跨进程 / 跨网络 / 跨主机；③ 并发、安全或凭据相关；④ 依赖本机或环境状态（端口、DNS、隧道、证书、权限）。
2. **必须先开探针 SBI**：这类工作**先交付一个探针**，探针只满足三条 —— ① **只回答一个可证伪的问题**（写成一句话 + 一条可复制的命令/脚本）；② **产物可丢弃**（不写 UI、不入词表、不补覆盖率、不做错误处理的产品化包装）；③ **结论落档**（判定 + 命令 + 原始输出片段）。
3. **探针不产品化，也不并入后续**：探针代码与产物不要求演进为正式实现；需要时可以整体丢弃（避免「临时方案变成事实标准」）。
4. **门禁**：探针结论为**通** ⇒ 才开**真实开发 SBI**；为**不通** ⇒ 先改设计并回写 spec，再决定是否开下一个探针。
5. **探针 SBI 同样受批次判据约束**（[`ADR-016`](ADR-016-sbi-delivery-granularity.md)）：有接收方（后续实现 SBI 或评审）、有可执行的判定、无跨批硬依赖。

## Rationale

- **探针把「不确定性」变成可丢弃的沉没成本**：最贵的不是失败的探针，而是**基于未验证假设**写下的结论、代码与文档 —— 本批那次误判的代价正是如此（错误结论进了台账与建议，需要专门一轮纠正）。
- **与 [`ADR-016`](ADR-016-sbi-delivery-granularity.md) 同向而不重复**：016 要求「高风险项各自单独成批」，017 进一步要求「这批**先做探针**」——隔离风险之后，还要先在最小面上证伪。
- **不选「写一份调研文档」**：调研任务没有可验收产物，容易漂移成阅读笔记；探针 SBI 必须给出**一条可复制的命令与判定**，可被他人复跑。
- **不选「直接开真实开发」**：这正是本批做过的那条路 —— 假设未验，错误结论就会向下游扩散。

## Consequences

- **正面**：不确定性在**最便宜的阶段**被消掉；真实开发的估算有了依据；错误结论不会写进 spec 与台账；结论以「命令 + 输出」形式沉淀，可被复跑。
- **代价**：同一件事多一个交付单元；探针与真实实现之间可能有一段「重复劳动」（需接受这部分被丢弃）。
- **风险**：探针被当成正式实现的开头，悄悄变成既成事实 ⇒ 以「可丢弃」与「不产品化」两条硬约束拦住；若确实要留用，则按真实开发 SBI 重新走一遍判据。
- **后续**：`sdd-scrum-practices.md` §2.4 已增补「探针 SBI」条目；在飞计划（[`web-portal/portal-identity-plan.md`](../web-portal/portal-identity-plan.md) §8）中的高复杂度项按本条重排。
