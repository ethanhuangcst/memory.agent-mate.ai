# ADR-019: 设计 spec 必须写明「基本设计约束」，且每条约束有可执行承接

## Status

Accepted

## Context

用户对 `PSP-W1` 的第四条经验（2026-09-23）：

> **质量太差，一堆 bug**。很多**低级错误**，没有在开发中就被捕获。再来一次的话：尽可能在 mockup 阶段就发现问题；**提高 e2e 测试覆盖率**；**完善设计**，在设计 spec 中写明白 **common sense 可以写出的基本设计约束**，例如 **CRUD 时重复 ID 应该如何处理**、**错误提示应该如何处理**等。

本批实证（都是「低级」且都逃逸到了用户手上）：

| 现象 | 缺失的那条基本约束 |
|---|---|
| 重名建用户时看不到任何报错（错误渲染在弹窗**外**，被遮罩盖住） | **冲突/重复**如何处理 + **错误提示出现在哪里** |
| 「停用用户还能签发令牌」被用户判定为缺陷 | **状态前置条件**：停用期间允许哪些动作（`D13` 只写了「可逆」，没写这一条 ⇒ 两种理解都能自圆其说） |
| 长值撑出弹窗边框（Issue 8） | **长内容**的呈现约束（不可断的长串如何处理）—— 事后才以护栏断言补上 |
| 弹窗点第二次就到 API 地址（Issue 5，相对链接） | **二次操作**（重复点击/刷新）的落点约束 |

**关键观察**：这些约束都不是「难想到」，而是**没有人写下来**；而实现一旦遇到未写明的场景，就必然**自行假定**一种行为 —— 假定与用户预期不一致时，才以「bug」的形式暴露。

另外，本批的**门禁在带病运行**：唯一能自动发现布局类问题的端到端入口（`scripts/portal-e2e.sh`）当时既**起不来**（缺必需配置键），又会**静默把测试跑在别人的实例上** —— 即「没有在开发中被捕获」有结构性原因，不只是注意力问题。

## Decision

1. **设计 spec 对每个 CRUD / 状态变更能力，必须显式写出四类基本约束及处理方式**（最小集，不得省略）：
   - **重复 / 冲突**：重复标识、重复提交（双击）分别如何处理；
   - **不存在**：目标对象已被删除 / 已变更时的行为；
   - **非法输入**：格式、长度、字符集、空值的边界与提示；
   - **并发与二次操作**：两窗口/两次提交、刷新重放、返回后重做时的状态与落点。
2. **每条约束必须有可执行的承接**：凡对用户可见的行为，至少一条**真实浏览器端到端**用例（不得用「集成测试通过」代替）；不可端到端者，写一条集成或单元断言，并登记理由。
3. **错误呈现必须写明位置与口径**：错误出现在**触发它的上下文内**、走四语言词表、且不泄露验签/内部失败原因（沿用既有安全口径）。
4. **状态前置条件必须显式**：每个动作行都必须写出「在哪些状态下可用 / 不可用」，以及不可用时给用户什么（隐藏入口 / 拒绝 + 文案）。
5. **未写明的约束不得由实现自行假定**：实现过程中若必须假定，则**先回写 spec 再实现**（把假定变成显式决定）。

## Rationale

- **把「common sense」变成 spec 的必填项**：这些约束的共同点是「写出来很便宜、漏掉很贵」—— 漏掉后由实现假定，再以 bug 的形式回到用户面前（本批 4 例）。
- **用「约束」而非「覆盖率数字」驱动 E2E**（用户第 3 条经验里的「提高 e2e 覆盖率」）：笼统提高覆盖率容易堆断言而不涨信息量；**按四类约束逐条配用例**既提高了覆盖率，又让每条用例都对应一条明确的设计承诺，可核对、可追溯。
- **不选「加强评审」**：评审依赖注意力与经验，这正是本批失效的地方；把它变成 spec 的必填项 + 可执行断言，才不依赖谁当天是否细心。
- **承认门禁本身也要养护**：本批已经吃过「门禁带病运行」的代价 ⇒ 端到端入口的可用性（起得来、不静默测错实例）本身是一条必须维护的约束（已由 `portal-e2e.sh` 的 fail-loud 修复落地）。

## Consequences

- **正面**：低级错误在开发阶段被捕获；验收有据可依（每条约束指得到一条用例）；实现不再需要对未写明场景「猜」。
- **代价**：设计 spec 变长、写 spec 变慢；每条约束配用例会显著增加用例数（本批离线用例已到 261 项，仍会增长）。
- **风险**：把「四类」写成形式主义（复制粘贴的模板句）⇒ 以「每条约束必须能指到一条用例」作为反形式主义的硬钩子；写不出用例的约束说明它还不是可验收的约束。
- **后续**：`web-design.md` 的认证模型与交互约束、`web-stories.md` 的 AC、`web-test.md` 的用例登记按本条补齐（见 [`web-portal/portal-identity-plan.md`](../web-portal/portal-identity-plan.md) §8 的 `SBI-D1`–`SBI-D3`）。
