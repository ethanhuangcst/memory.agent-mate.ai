# ADR-016: 交付批次颗粒度从 PSP 级降到 SBI 级

## Status

Accepted

## Context

`PSP-W1`（Sprint 4 `#2`）以 **PSP 批次**形态交付（批次口径见 [`sdd-scrum-practices.md`](../sdd-scrum-practices.md) §2.4）。它的**书面判据只有一件事**：

> 本地可完成「管理员建用户 → 签发令牌 → 列出元信息 → 轮换 → 吊销即时失效」闭环，且非管理员无法创建用户或令牌。

但同一批**实际装载**的内容（证据见 [`sprint-backlog.md`](../sprint-backlog.md) Sprint 4 `Retrospective`，含三轮「同日补充」）：

| 序 | 实际装载的增量 | 本可独立交付 |
|---|---|---|
| 1 | 门户实现落地（建用户 / 签发 / 列出 / 轮换 / 吊销） | 是 |
| 2 | 两条本机测试路径（快速路径 + 真身份路径）与 `--dev-login` | 是 |
| 3 | cloudflared 隧道 + **Cloudflare Access 真身份**（C） | 是（且技术复杂度最高） |
| 4 | 受限**开发登录入口**（A） | 是 |
| 5 | **401 页自诊断**（B） | 是 |
| 6 | 覆盖率门禁（v8 provider + 阈值 + 缺口补测） | 是 |
| 7 | UI 迭代三轮（色系 / 版式 / 外框冻结） | 是 |
| 8 | 登录身份收口（真实邮箱 + 生产身份来源白名单）与 **ADR-015** | 是 |
| 9 | 弹窗版式重做与布局护栏（Issue 8） | 是 |

**判据一行没变，装载量翻了几倍。** 由此出现的具体代价：

1. **反馈来得太晚**：`Issue 6 [FATAL] 无法登录` 直到批次中段才暴露 —— 因为「**人能不能登录**」这个最基础、最该先交付的增量，被排在一堆别的增量之后；期间的自认为「已验」还建立在 curl（请求头）与 Playwright（程序化 cookie）上，**两者都绕过了人手**。
2. **载体被迫持续扩张**：Sprint 4 的回顾出现三轮「**同日补充**」（UI 迭代轮 / `PSP-W1` 实现轮 / 身份收口）—— 每出现一次，就是一批在收口期又吸收了新工作，而它的判据与证据没有同步重述。
3. **归因变难**：回顾只能按「批次」写，无法指出是哪个增量出的问题。
4. **风险不隔离**：最高技术复杂度的两项（隧道 + 真身份、身份收口）与普通功能同批 ⇒ 任一卡住都会拖住整批的可验收性。

用户结论（2026-09-23，定稿口径）：

> 颗粒度太大，导致增量交付遇到很多问题。经验：有技术复杂度高的功能，也包含了太多功能。再来一次的话：**分解到颗粒度更细的 SBI**。

## Decision

1. **批次口径由 PSP 细化为 SBI，而非取消 PSP。** 新建批次按 **SBI** 编排；[`sdd-scrum-practices.md`](../sdd-scrum-practices.md) §2.4 的四条判据（有接收方 · 有端到端判据 · 无跨批硬依赖 · 不是任务清单）**全部保留**。
2. **SBI 的范围判据（可机械核对）：**
   - **单一角色 × 单一动作**：一个 SBI 只让某类角色**多做/能做一件事**；
   - **技术复杂度隔离**：一个 SBI 最多**首次引入一项**技术 / 依赖 / 外部系统 —— 隧道与真身份接入、跨进程桥（stdio）、并发与安全机制等高风险项**各自单独成批**；
   - **收口期不得扩张**：批次收口期内新发现的工作必须登记为**新 SBI**，不得以「同日补充」并入正在收口的批次。
3. **既有 `PSP-*` 批次不重排**：历史与已交付批次不改（ADR 不可变、已交付事实不改），本决定**只对后续工作生效**。
4. **落点**：判据写入 [`sdd-scrum-practices.md`](../sdd-scrum-practices.md) §2.4；后续 Sprint 的 ToDo 行按 SBI 给出；在飞计划（如 [`web-portal/portal-identity-plan.md`](../web-portal/portal-identity-plan.md) 的阶段 2/3）**按 SBI 重排后再执行**。

## Rationale

- **不维持 PSP**：本批实证显示，PSP 判据只约束了「这批交付给谁」，**没有约束这批装多少** —— 于是判据与装载量脱节，反馈与缺陷暴露被推迟。
- **不退回「任务行」**：§2.4 早已论证 PSP 相对任务清单的确定性收益（有接收方、有端到端判据、禁止动作词命名）；退回任务视角会把「可交付给谁」这一层丢掉。
- **选 SBI**：保留 PSP 的**形式**收益（接收方 + 端到端判据 + 无跨批硬依赖），只把**范围**收到「一件事」；「一件事」这一约束可机械核对（单一动作、首次引入 ≤ 1、收口期无新增），不依赖主观判断。
- **复杂度隔离优先**：用户点名的第一条经验就是「有技术复杂度高的功能」。把它单列成批，才能让它的风险**不污染**普通功能的可验收性。

## Consequences

- **正面**：可验收的增量出现得更早（基础可用性不再排在最后）；FATAL 类缺陷更早暴露；高风险项与其他增量互不阻塞；回顾可按 SBI 归因。
- **代价**：批次数量增加 ⇒ 追踪与编排开销上升；Sprint 内需要显式编排 SBI 顺序；「收口期禁止扩张」意味着跨批的小改动要多走一次登记（换来可归因）。
- **风险**：SBI 过细会导致事务性开销压倒收益 ⇒ 以「**能否独立验收**」为下限判据：若两件事必须同时验收才算完成，它们就是**一个** SBI。
- **后续**：`sdd-scrum-practices.md` §2.4 已增补 SBI 判据；`sprint-backlog.md` Sprint 4 `Retrospective` 已记录本轮复盘；`portal-identity-plan.md` 的阶段 2/3 已按 SBI 重排。
