# 3.14 mcp:全链路「写入 → 用户库 → 召回」判决据探针（Sprint 4 `3.6` 的开工前置）

> **研究类探针，不入制品**（[`ADR-017`](../../specs/adr/ADR-017-complexity-probe-before-real-build.md)）。为 Sprint 4 `3.6`「mcp:全链路联通」定档判决据：**「一次写入召回跑通（门户 → HTTP MCP → 子进程 stdio → 用户库）」的强判据怎么写**，以及**哪些写法会必然假失败**。
>
> 交付对象：本 Sprint `3.6`；判据口径落 [`../../specs/mcp/mcp-test.md`](../../specs/mcp/mcp-test.md) §4-F / §4-G 与 [`../../specs/mcp/mcp-design.md`](../../specs/mcp/mcp-design.md) §5.6.2。

## 为什么必须先用探针

`3.6` 的验收条件写着「一次写入召回跑通 … → **用户库** 全程贯通并返回真实结果」。已有的真上游门禁（`make portal-mcp-probe`，`3.1` 交付）断言的是**同一个会话内**的「写入成功 + 召回命中 + 库文件落在该用户目录」—— 而**同一进程内的召回可能是内存索引给的**，**不能**证明「写入真的落进了用户库」。全仓此前**没有任何地方**验过「换一个会话 / 新进程仍能召回」（已 grep 确认）。

## 跑法

**自包含**（本目录自带 `node_modules`，不需要门户）：

```bash
cd memory.agent-mate.ai/probes/full-chain-probe
npm install
node probe.mjs
```

| 项 | 值 |
|---|---|
| 退出码 | `0` 全部断言通过 · `10` 前置不足（容器未运行 / 取不到 endpoint 或上游 key）· `30` 断言失败 |
| 原始输出 | `out/probe-run*.log`（**不入库**） |
| 拓扑 | **不经门户**：直接起 stdio 会话（`docker exec` 借壳），把变量压到最少（同一库路径、**不同进程**）⇒ 结论唯一归因。「门户链路」（令牌 → handle → 库路径）已由 `make portal-mcp-probe` 证过；`3.6` **交付时**把同一判据挂到门户链路上 |
| 副作用 | 在容器内**预建并删除** `/data/users/probe314`（借 root；不碰其它用户），**真写两次**（走真 embedding） |

## 七项判据（实测）

两轮复跑：**7/7 断言 PASS、退出码 `0`**，结论一致。

| # | 判据 | 实测 |
|---|---|---|
| Q1a | 会话 A 写入成功 | ✅ |
| Q1b | 会话 B 是**另一个进程** | ✅ `A=18781 · B=18789`（复跑 `18861/18866`） |
| **Q1c** | **新进程**能召回上一个会话写入的记忆 | ✅ 回包含该标记 ⇒ **「写入落进用户库」成立** |
| **Q4** | **反向对照**：从未写入的标记**不出现在**回包里 | ✅（防空转） |
| Q2 | 库文件在该用户目录（同用户两会话共用） | ✅ |
| **Q3** | **不优雅收尾**（直接 `close()`）后仍能召回 | ✅ ⇒ 判决据**不**依赖「先 `terminateSession`」 |
| Q5 | 四个会话收尾后容器内无同形进程 | ✅ `0` |

## 由结论导出的硬约束（`3.6` 直接照用）

| 要判的事 | 判据实现 |
|---|---|
| 全链路「写入 → 用户库 → 召回」 | 会话 A 写唯一标记 → 收尾 → **会话 B（新进程）**召回 ⇒ **回包文本含该标记**。不需要先 `terminateSession`（Q3 实测） |
| **禁止**按 `count` 判 | `memory_recall` 是**语义混合检索**，`count` = **返回条数**而非精确命中数：从未写入的标记**同样**会有相关命中（`count:0` **永不出现**）；库里多一条记忆时 `count:1` 会变 `count:2` ⇒ 按 `count` 写的断言**必然假失败**。判据一律写「**回包里有没有那个标记**」 |
| 判据要防空转 | 必须带**反向对照**（「从未写入的标记不出现在回包里」），否则「怎么都能命中」的假阳性无法被发现（本轮首版就是因此才暴露 `count` 陷阱） |

## 边界与如实登记

- **不经门户**（见上）；`3.6` 交付时在门户链路上复述同一判据。
- **一处既有脆弱点（不是缺陷，已登记）**：`scripts/portal-mcp-probe.sh` 的 `memory_recall` 断言写的是 `count:1`（`tests/fixtures/probe-runner.mts`）。它**现在稳**，因为该脚本每次在清理阶段 `rm -rf /data/users/$HANDLE`（`portal-mcp-probe.sh:59`）⇒ 每次都是空库；但判据本身**脆** —— 一旦「一个会话写两条」或清库被去掉，就会假失败。`3.6` 顺手把它改成**按标记判**。
- 本探针**不改**产品代码（本轮只做开工准备）。
