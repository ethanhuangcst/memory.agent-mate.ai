## 为什么单列

`4.4` 的验收条件是「三段指南齐备（Cloudflare Access / SSH 密钥对与 forced command / 对象存储私有桶与子账号）+ **每步验证点** + **可照做**」。文档不能被执行，于是「可照做」最容易被写成一句**无法证伪**的话。但对一份**配置类**指南，「照做会得到什么」里有一大半是机械可判的：

| 问题 | 判据 |
|---|---|
| Q1 指南要求读者填的键，与**代码真正会读**的键是不是同一套？ | 漏一个 ⇒ 读者照做后**静默失败**（门户 `4.3` 的启动自检 fail-closed 会拒绝启动，属响亮失败） |
| Q2 指南引用的**仓库路径**是不是都存在？ | 54 个引用逐个 `existsSync` |
| Q3 指南自己承诺的「**逐键一致**」成不成立？ | `deployment.md` §5.4 与 `../deploy/.env.prod.example` 逐键比对 |
| Q4 指南提到的键里有没有**真源已经不认**的？ | 只作**发现**（多半是上游 `config.toml` 的键，需人工判有无陈旧） |

## Q1 的「真正会读」怎么判（2026-09-25 判据修正）

**旧口径** = 扫 `admin_portal/src/**` **全文**抽 `PORTAL_*` 令牌 ⇒ 把**注释 / 字符串里提到的将来键名**也算成「会读的键」。实测后果：`PORTAL_CONTACT_EMAIL` 只出现在 [`../../admin_portal/src/web/routes/index.ts`](../../admin_portal/src/web/routes/index.ts) 的一条注释里（「如需按部署改地址，再加 `PORTAL_CONTACT_EMAIL`」，由 Sprint 4 `#4.2` 交付引入，代码并未读取），却让 `A2` 在 HEAD 上**假红**（`4 PASS / 1 FAIL`，退 `30`）。

**新口径** = 只认三种**真读取**形态（本仓现状：`admin_portal/src/config.ts` 是唯一入口，`RawEnvSchema.safeParse(env)` 后取 `raw`）：

| # | 形态 | 正则 |
|---|---|---|
| ① | zod schema 的对象键 | `/^\s*(PORTAL_[A-Z0-9_]+)\s*:/` |
| ② | 解析后的引用 | `/\braw\.(PORTAL_[A-Z0-9_]+)\b/` |
| ③ | 直读环境变量（当前 0 处，留作防回归） | `/\bprocess\.env\.(PORTAL_[A-Z0-9_]+)\b/` |

三种形态**逐行**匹配（不跨行、不吞字符串）⇒ 注释里的键名不会被当成读取。

**收窄带来的新风险与对策**：只收窄会留下「有人靠改注释消红」的口子 ⇒ 新增 `A2b`：源码里出现的**每个** `PORTAL_*` 令牌**要么是真读取、要么在白名单里带理由**（白名单条目必须**仍被引用**，否则报「陈旧白名单」）。即：注释里的键名不会静默假红，但**必须被显式解释**。

**残余边界（如实登记）**：动态拼接读取（形如 `process.env[someVar]`）**不在**判据内 —— 这类形态不产生键名令牌，属覆盖之外；`A2a`（`raw.X` ⊆ schema 键）可兜住「读了却没声明」的一半。

### 决定性发现（`A2` 首跑红的根因，已是历史）

1. **`deploy/docker-compose.prod.yml` 只有上游两个服务**（`ai-memory` / `curator`），**没有门户 stack**；门户 compose 是「部署动作：新建 `/opt/ai-memory/` 下门户 compose」（**在服务器上现写**，不入仓）。
2. **门户 stack 的 env 真源只有 1 个键**：`deploy/portal.env.example` 只有 `DASHSCOPE_API_KEY`；而门户代码真正会读 21 个 `PORTAL_*`（`admin_portal/src/config.ts` 的 `loadConfig`）。
3. 这 21 个键的**唯一登记处是设计文档** [`../../specs/web-portal/web-design.md`](../../specs/web-portal/web-design.md) §12.9（关键配置项），**不在**部署真源、**不在**部署指南 ⇒ 读者照 `deployment.md` §12.2 做，**无从知道门户 stack 要填哪些键**（好在 `4.3` 的启动自检 fail-closed ⇒ 会**响亮失败**而不是静默错配）。该缺口已由 `4.4` + `portal.compose.yml` 入仓补齐（`A2` 转绿）。

## 由结论导出的硬约束（`4.4` 直接照用）

1. **每段指南的「验证点」必须是能跑出确定性结果的命令**（例如：CF Access 段的验证点 = 未认证被拦 **302** / Service Token 直达 **200** / 在线套件退出码 `0`；SSH 段的验证点 = `ssh` 能进、但 `bash` 被 forced command 拦；对象存储段的验证点 = 回读比对 + `make secret-check` 通过 + `AK` 不入仓）。
2. **门户 stack 的 `PORTAL_*` 清单必须进指南**（并在 `portal.env.example` 里逐键登记）—— 这条由 `A2` 判据把住。
3. **「逐键一致」这类承诺要写成可机械判定的**（`A4` 就是范例：它把 §5.4 的一句话变成了会红的断言）。
4. **键 / 路径的引用一律用相对路径**：`A3` 能成立是因为文档里的 54 个引用都是可解析的相对路径。
