## 踩坑（本批最有价值的一条）

**判据自检抓出「假通过」**：`S1` 首版夹具是「用 `sqlite3` 分两次执行 SQL 造 WAL 数据」，结果**裸 `cp` 也被判成「对」**
⇒ `S1` 红。根因：SQLite 在**最后一个连接关闭时**会做 checkpoint ⇒ `-wal` 被合并/清空 ⇒ 裸 `cp` 也能拿到完整数据。
⇒ **修法**：夹具必须让库处于**「被占用」**状态（`mkfifo` 挂一个常开的 `sqlite3` stdin + `PRAGMA wal_autocheckpoint=0`）。
**一般规则**：并发/状态类判据的夹具，必须复现**生产上的状态条件**（这里是「库一直被进程占用」），
否则判据会**静默假通过** —— 而只要判据自带正/反对照自检，这种假通过就会当场暴露。

## 与本体（`backup/`）的分工

- 探针：**只读**，判「判据本身可判 + 入口指向真实文件」，本机可跑，**不碰生产**（临时产物只落 `${TMP}`）。
- 本体：真正做备份/恢复；其自测证据见 [`../../backup/README.md`](../../backup/README.md) §4。
- 两者**独立实现**同一语义的判据（探针不调用 `backup/` 的脚本）⇒ 避免「拿自己的实现证明自己」。
