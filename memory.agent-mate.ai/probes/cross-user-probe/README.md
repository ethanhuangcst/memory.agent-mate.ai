# 3.15 mcp:跨用户隔离取证探针（Sprint 4 `3.7` 的开工前置）

> **研究类探针，不入制品**（[`ADR-017`](../../specs/adr/ADR-017-complexity-probe-before-real-build.md)）。为 Sprint 4 `3.7`「mcp:跨用户隔离」定档判决据：**「用户 A 写入的记忆，用户 B 经同一门户实例检索不可见」这条验收条件，判据怎么写、又拿什么证明它不是空转**。
>
> 交付对象：本 Sprint `3.7`；判据落 [`../../specs/mcp/mcp-test.md`](../../specs/mcp/mcp-test.md) §4-F 的 `3.7` 落点（用例 `TC-M-L1-03` / `TC-M-L1-04`）与 §5 版本记录。

## 为什么必须有它（覆盖核对结论）

`3.7` 的两条验收条件是「A/B **经同一门户实例**互不可见」与「**两侧均记录解析后的库路径**」。既有取证**都有缺口**：

| 既有取证 | 证到了什么 | 缺口 |
|---|---|---|
| `scripts/iso-probe.sh`（Sprint 3，`V2` / `V3` / `V4` 的本地版） | **上游级**隔离：交叉 `get` 取不到、漏设 `AI_MEMORY_DB` 时解析到共享主库被拦、显式 env 后 `source == 该用户库`、目标库变化而主库不变 | 它是**用显式 env 直连上游** ⇒ **没有经过门户**。而「令牌 → handle → 库路径」这一步**恰恰在门户**（`R1`「致命：多用户隔离可能静默失效」/ `R2`「隔离完全依赖门户一处正确性」指向的就是它） |
| `make portal-mcp-session-probe`（`3.3` / `3.4`） | 经门户的两个用户会话：进程数 / PID / 各自 env、用户目录之外零新增、库句柄归零、收尾无僵尸 | 验的是**进程与文件隔离**，**从没让 B 去召回 A 写的东西** ⇒ 检索可见性这一面未被端到端取证 |

⇒ 本探针补的正是那一段：两个**不同用户**、两条**不同令牌**、**同一个门户实例**。

## 跑法

```bash
# 前置：容器常驻 + 门户依赖已装 + 端口 8801 空闲
bash memory.agent-mate.ai/probes/cross-user-probe/probe.sh
```

| 项 | 值 |
|---|---|
| 退出码 | `0` 全过 · `10` 前置不足（容器未起 / 依赖未装 / 端口被占 / 取不到 docker endpoint 或上游 key）· `20` 门户起不来 · `30` 断言失败 |
| 覆盖 | `PROBE_PORT=`（默认 `8801`，与会话探针的 `8799`、`3.1` 的 `8798` 错开）· `PROBE_CONTAINER=` |
| 原始输出 | `out/probe-*.log`（**不入库**） |
| 副作用 | 容器内**预建并删除** `probe37a` / `probe37b` 两个用户目录；起一个**临时门户**（库在 `/tmp`，端口 8801），收尾 kill 并**复验**端口释放 + 容器内归零 |

## 七项判据（实测：两轮复跑均 **7/7 PASS、退出码 `0`**）

| # | 判据 | 实测 |
|---|---|---|
| X1 | A 经门户写入成功 | ✅（回包给出记忆 id，X5 用它） |
| **X2** | **B 经同一门户实例召回 A 的标记 ⇒ 回包不含** | ✅ 上游回 **`count:0`**（空结果）⇒ A/B 互不可见（正向） |
| **X3** | **灵敏度对照**：B 能召回**自己**写的 | ✅ `count:1` ⇒ **X2 不是「B 的检索根本不可用」造成的假通过** |
| X4 | 反向：A 召回 B 的 ⇒ 不含；A 召回自己的 ⇒ 含 | ✅ **双向**成立（`TC-M-L1-03`） |
| **X5** | B 用 **A 的记忆 id** 调 `memory_get` | ✅ 上游回 **`memory not found`**（`TC-M-L1-04`） |
| **X6** | 门户 `audit` 表两侧各一行 `mcp_session_opened`，`detail_json.dbPath` 各自正确且不同 | ✅ `A=/data/users/probe37a/ai-memory.db` · `B=/data/users/probe37b/ai-memory.db`（命中 2 行） |
| X7 | 两侧库文件都真实存在于容器内（同 uid 可读） | ✅ |

**顺带实测**：core 档 8 个工具名 = `memory_store, memory_recall, memory_search, memory_list, memory_load_family, memory_smart_load, memory_get, memory_capabilities` ⇒ 「按 id 直取」的工具就是 **`memory_get`**。

## 由结论导出的硬约束（`3.7` 直接照用）

1. **判据必须落「经同一门户实例」**：两条令牌、一个门户；直连上游的取证（`iso-probe.sh`）**不能替代**它。
2. **召回类判据一律按「回包里有没有那个标记」判，禁止按 `count` 判**（`3.14` 的教训；本探针的 X2 恰好会得到 `count:0`，但**那不能当判据用** —— 空库与「查不到」在 `count` 上无法区分）。
3. **每条否定型判据必须配一条「必须为正向」的灵敏度对照**（X3）：否则「B 的检索坏了」也会让 X2 变绿。
4. **「两侧记录解析后的库路径」可以直接从门户库读**：`audit(action='mcp_session_opened')` 的 `detail_json.dbPath`（机制由 `3.4` 交付）⇒ 断言两侧各一行、各自指向 `/data/users/<自己>/ai-memory.db` 且**互不相同**。

## 边界与如实登记

- 只用**两个**用户、两条令牌；**不测**同一用户多会话落在同一库上的并发写（归 `4.1` 的并发上限）。
- 「每库属主为 `aimem`」是 `#4` 的既有口径（文件属主），**不在本探针**。
- 探针脚本由 `3.3` 的 `portal-mcp-session-probe.sh` **派生**（改端口 / 用户名 / 断言体 / 文案），**不是**产品侧入口；产品侧是否把这三类判据挂进既有门禁，见 `3.7` 的开工准备计划。
