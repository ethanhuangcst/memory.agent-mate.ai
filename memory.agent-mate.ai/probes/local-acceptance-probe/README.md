## 结论（2026-09-25 实测，两轮一致 · **9/9 PASS · 退出码 0**）

| # | 场景 | 结论 | 关键观测 |
|---|---|---|---|
| S1 | **面隔离** | ✅ **本机可判**（本机两个「面」= 两个 `Host`：`PORTAL_ADMIN_HOST=localhost` / `PORTAL_MCP_HOST=127.0.0.1`） | 用**构造的 Host 头**：`/mcp`@管理面 ⇒ **`403` + `Forbidden: request host does not match this face.`**；`/admin/users`@MCP 面 ⇒ `403` vs 管理面 ⇒ `401`（**灵敏度对照**：同一条 `/mcp` 在对的 Host 上是 `401` 而非 `403`） |
| S2 | **并发上限（真上游）** | ✅ **可判** | 同一令牌第二路 ⇒ **`429` + `SESSION_LIMIT_EXCEEDED`**，子进程 **4→4**（不新增）；第一路确实建了 **1** 个子进程（基线对照） |
| S3 | **吊销即时生效（真上游）** | ✅ **可判，且确定性** | 机制是 `route.ts:248` 的**请求驱动惰性回收**：**吊销本身不杀进程**（4⇒4，这条是前提对照）；随后带「该会话自己的 `sessionId`」的请求 ⇒ **`401`** 且**该会话的子进程被回收**（4⇒3） |

## 顺带发现（探针带出来的，值得登记）

1. **门户有「请求体上限」且契约里没登记**：`src/server.ts:75` `bodyLimit: 64 * 1024`（**代码常量、不可配**）
   —— 它是背压上限的**入站对偶**（入 64 KiB / 出 4 MiB）。首版用 ~86 KiB 的 `memory_store` 直接被
   **`413 FST_ERR_CTP_BODY_TOO_LARGE`** 拦在门外 ⇒ 判据设计时**内容量必须落在两个上限之间**。
2. **面不匹配的信号是 `403` + 英文串**（不是 401 / 404）⇒ 面隔离的真上游判据可以直接断言这个串。

## 三条工程教训（本轮实测换来的）

- **`keyPrefix` 只能从库里取**：`issueKey()` 的返回值里**没有** `keyPrefix`（首版据此直接 `revokeKey`
  ⇒ `key-not-found`，判据假失败）⇒ 用 `listKeysForUser(db, handle)` 找 `revoked_at === null` 那一把。
- **判据的输入量要落在两个上限之间**（见上第 1 条）：只想着「触发背压」而忽略**入站**上限，会让判据在
  到达被测点之前就失败。
- **派生脚本的固定文案要当代码改**：`3.15` 那轮同款问题（成功文案仍写 `3.3` 的判据）⇒ 本轮先改文案再跑。

## 边界（如实登记）

- **真实域名下的面隔离**（CF Access / 隧道）不在本探针：本机只证「按 `Host` 分面」这一层；域名与
  证书链相关判据归 Sprint 5 上线验收。
- **经门户的配额透传**（改 `[limits]` 后超限被拒）归 Sprint 5 `#2`「mcp:配额透传」—— 本行只判并发上限。
- **「多条 × 正文」的批量体量**仍未测（同 `3.18` 的登记）⇒ 背压上限取值仍按最坏情形估算。
- 面隔离的 `/admin/users` 在管理面上是 `401`（**未带身份**）⇒ 本探针只判「面是否分得开」，不判管理面鉴权
  （后者由离线用例与生产验收覆盖）。
