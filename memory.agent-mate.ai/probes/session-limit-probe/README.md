## 由结论导出的硬约束（`4.1` 直接照用）

1. **容器内存上限 = 未设置**（`docker inspect` 的 `HostConfig.Memory` 实测为 `0`）⇒ **没有任何容器级护栏**，门户侧的并发上限是**唯一**的约束 ⇒ 本行的取值要按**服务器可用内存**倒推（每会话 ~27 MiB）。
2. **取值有据**：每会话 **~27 MiB** + 真调用延迟在 4 路并发的墙钟 **~0.75 s**（1 路 ~0.54 s）⇒ 1–5 人规模的护栏可给 **每 key 1–2 · 全局 4** 一类的保守初值（**本探针只给依据，不代替 `4.1` 的定值**）。
3. **「不排队致死」的判据形状**：超限时必须**立即**返回拒绝 —— 观测面 = **HTTP 码 + 响应时间 + 不新增子进程**（「立即」= 响应时间远小于一次真 embedding 的墙钟 ~0.5 s，且**不出现队列长度增长**）。`4.1` 的用例应把这三项一起断言（只断状态码会漏掉「其实排了队」）。
4. **「额度内不受影响」的基线**：4 路并发下每会话仍在 ~0.75 s 内完成 ⇒ 护栏**不应**给额度内的请求增加等待（判据可写「额度内并发下延迟 ≤ 基线 × 常数」）。
5. **收尾必须归零**：护栏不能靠「不回收」实现（A6 是基线）。

## 边界与如实登记

- **不经门户**：本探针测的是「上游每个会话进程的开销」，**不测**门户的并发语义（那是 `4.1` 的实现 + 其用例的事）。
- **容器内存上限未设置** ⇒ 「按内存倒算可容纳会话数」这一步在**本机无意义**（无上限可倒算）；结论里只给「每会话 ~27 MiB」这一**实测**值，把倒算留给 `4.1` 按**服务器**内存定值。
- 延迟数据含**真 embedding 的网络往返**（同一台机、同一 key），**不代表生产延迟**；它只用来定「额度内不受影响」的**相对**基线。
- **不改**任何产品代码（`admin_portal/src/` 一行未动）。
